# Azure pilot deployment

`foundation.bicep` creates the isolated shared resources for the Murmur pilot. `apps.bicep` deploys the immutable backend and frontend images after the required credential values have been written to the generated Key Vault. The backend revision contains one HTTP/WebSocket API container running `VOICE_RUNTIME=websocket_v1`; no managed-media worker or LiveKit service is part of the deployment topology.

The apps use separate managed identities. The backend identity can pull its image and resolve only two active runtime secret scopes: Azure OpenAI and Firebase. The frontend identity is pull-only and cannot read backend credentials. Both identities use lifecycle `None`, so Azure can perform those platform operations without exposing an identity token endpoint to application code.

Use `scripts/deploy_azure.py`; it validates git provenance, imports secrets without printing them, performs the builds, deploys both apps, and verifies the live result. Set `MURMUR_AZURE_SUBSCRIPTION_ID` and `MURMUR_AZURE_TENANT_ID` to the exact GUIDs for the intended target (or pass their equivalent CLI flags); the driver refuses a different active Azure account. Do not pass provider credentials as command-line arguments or Bicep parameters.

The deployer refuses any unrecognized direct Key Vault writer assignment for its operator. It grants itself secret-write access only around staging and post-health finalization, then reconciles removal of the exact temporary assignment in all exit paths. A renewable, finite lease on a private Azure Blob serializes the credential, build, and application transaction across machines; a second deploy refuses while the lease is held, and a crashed deploy recovers by lease expiry. Image builds use unique, unguessable tags before resolving immutable digests, so releases cannot race on a shared source-SHA tag.

`FIREBASE_RUNTIME_SERVICE_ACCOUNT_PATH` must point to a dedicated Firebase Authentication Viewer credential. Before writing it, the driver asks Google Cloud IAM for the credential's effective Firebase Authentication permissions across the documented Firebase Authentication permission set and requires exactly `firebaseauth.configs.get` and `firebaseauth.users.get`. The active `firebase-runtime-service-account-json` value is the only Google credential referenced by the deployed app. `FIREBASE_DOMAIN_ADMIN_SERVICE_ACCOUNT_PATH` is optional, must identify a different principal and key, and is used only by the local deploy process when the Container Apps hostname is not already authorized.

Each backend revision references the exact two staged Key Vault versions rather than mutable latest values. Rotation is finalized only after the new backend is healthy and every older revision has zero replicas in a terminal inactive state. After that cutover proof, the deployer revokes backend access to the retired LiveKit, Voice V2 signing, Deepgram, Groq, and ElevenLabs secrets and disables all of their versions. It also disables every version of the legacy `firebase-service-account-json` secret. Disabled versions remain recoverable to privileged Azure operators; this process does not delete provider credentials or revoke the corresponding Google service-account key.

The API exposes the authenticated, one-use-ticket WebSocket canary directly through Container Apps ingress. The first deployment proof remains provider-free: it must hold the exact source-pinned socket open for at least 310 seconds with no reconnect before any speech or model provider is attached.

The visual-and-voice pilot is intentionally limited to one API process and one always-on replica per app. Keeping both minimums at one avoids the measured 16-30+ second Container Apps cold starts and is required while one-use tickets and active-call ownership are process-local. Its SQLite database and replica-local volume are still ephemeral because SQLite locking is not safe on the SMB-backed Azure Files mount. Stored agents and history survive ordinary idle periods but can reset on restart, reschedule, or deployment; move to PostgreSQL plus migrations and a shared session store before treating data as durable or raising the replica maximum.
